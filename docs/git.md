# Контроль версий (Git)

Репозиторий использует Git. Основная ветка: `master`.

## Основные команды

| Команда | Назначение |
|---------|------------|
| `git status` | Проверить состояние рабочей области и индекса |
| `git log --oneline` | Посмотреть историю коммитов (кратко) |
| `git diff` | Посмотреть неиндексированные изменения в рабочей области |
| `git diff --cached` | Посмотреть индексированные изменения (готовые к коммиту) |
| `git add <путь>` | Добавить файл(ы) в индекс для коммита |
| `git commit -m "<сообщение>"` | Создать коммит из индексированных изменений |
| `git branch --show-current` | Показать имя текущей ветки |

## Соглашения по коммитам

Используйте префиксы в начале сообщения коммита:

- `feat:` — новая функциональность
- `fix:` — исправление ошибки
- `docs:` — изменения в документации
- `refactor:` — рефакторинг без изменения поведения
- `test:` — добавление или изменение тестов
- `chore:` — обслуживающие изменения (сборка, CI, конфигурация)

Пример: `git commit -m "feat: integrate ApplicationCore into Slint launcher"`

## Порядок работы перед коммитом

Перед созданием коммита обязательно выполните проверки качества:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

Все проверки должны пройти успешно. Не коммитьте, если есть неисправленные предупреждения Clippy или не проходящие тесты.

## Исключённые из отслеживания файлы

Следующие каталоги и файлы не попадают в Git (см. `.gitignore`):

- `target/` — результаты сборки Cargo
- `.env`, `.env.*` — локальные файлы окружения с секретами
- `*.log` — файлы логов
- `*.db`, `*.db-shm`, `*.db-wal` — файлы SQLite
- `*.pdb`, `*.msi`, `*.exe` — бинарные артефакты Windows
- `graphify-out/cache/` — кэш graphify
- `graphify-out/.graphify_*` — промежуточные файлы graphify
- `graphify-out/cost.json` — счётчик токенов graphify

## Связь с этапами разработки (PLAN.md)

Коммиты должны соответствовать этапам из `PLAN.md`. Например:

- `feat: complete Phase 4.1 ApplicationCore integration into launcher`
- `feat: wire LocalStore into launcher for settings persistence`
- `feat: add free space checking to installation crate`

Не коммитируйте частично реализованный функционал, который не проходит проверки качества.

## Правила пуша в GitHub

### 1. Все изменения в `main` только через Pull Request

Прямой_push (`git push origin main`) в основную ветку запрещён. Любое изменение, даже незначительное, должно быть оформлено как Pull Request и просмотрено перед слиянием.

Рабочий процесс:

1. Создайте тестовую ветку от `main`: `git checkout -b feature/<имя>`
2. Внесите изменения и закоммитьте их.
3. Запушьте тестовую ветку: `git push -u origin feature/<имя>`
4. Создайте Pull Request из `feature/<имя>` в `main` на GitHub.
5. Дождитесь прохождения проверок качества (fmt, clippy, тесты) и ревью.
6. После approuвмента смержите PR в `main`.

### 2. Незаконченный проект пушится только в тестовую ветку

Если функционал ещё не завершён, не прошёл все проверки качества или не готов к слиянию, код должен находиться исключительно в тестовой ветке (`feature/*`, `test/*`, `wip/*`), а не в `main`.

- Не пушьте незаконченный код напрямую в `main`.
- Не создавайте коммиты в `main`, которые ломают сборку или тесты.
- Тестовые ветки могут содержать промежуточную работу, но несливаются в `main` без завершения этапа и прохождения всех проверок.

### 3. Проверки перед созданием PR

Перед открытием Pull Request обязательно выполните:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

Все проверки должны пройти успешно. PR с неисправленными предупреждениями Clippy или не проходящими тестами не принимается.

### 4. Исключения

Исключения из правила «только через PR» возможны только по прямому согласованию с維護щиками репозитория и только для критических исправлений (hotfix), которые также должны быть оформлены как отдельный PR после применения.
